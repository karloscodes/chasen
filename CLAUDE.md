# Chasen

Deploy the Docker image of an app with a SQLite database to one server. Two programs, one repository. Open source, Apache 2.0.

| Program | Directory | Job |
|---|---|---|
| `chasen` | `cmd/chasen` | The CLI on the developer's machine: `client.go` (options, dispatch), `login.go`, `deploy.go`, `registry.go`, `placement.go`, and the screen of `chasen` with no command: `tui.go` (state, keys, loop) and `tui_view.go` (drawing) |
| `chasen-server` | `cmd/chasen-server` | Runs on each server: API, image pulls, backups, live replica, activity feed |

Shared code:

- `protocol`: the contract between the CLI and the server. The command list, the exit marker, and the API client live here and nowhere else. Another repository imports this package and answers the same API.
- `oauth`: the OAuth 2.0 device login. The server mounts it, and another repository does too.

Both packages are public API of the module: another repository imports them. Do not break them without a new version.

## Commands

```bash
mise run test     # go vet + unit tests, no Docker
mise run e2e      # full test with real Docker, the proxy, an S3 store, and a private registry. Needs sudo
```

Run `mise run e2e` after a change to the protocol, the deploy, the backups, or the login. It takes about 4 minutes. It skips itself when a `matcha-proxy` or `chasen-server` container exists, and it fails when another job replaces the proxy during the run.

## Decisions (do not reopen without the user)

- One protocol, two ways to the API (user, 2 October 2026). The CLI talks to an HTTP API with text output, not gRPC. It reaches that API on the web (`https://api.<domain>`), or through SSH (`ssh://root@203.0.113.5`, typed as `root@203.0.113.5`): the CLI runs the `ssh` program, which runs `chasen-server connect` on the server, and that joins the connection to the API (`protocol/ssh.go`, `cmd/chasen-server/connect.go`). SSH is only the transport: the CLI never runs loose commands on a server, and every command still has its token, its lock, and its history. The SSH way needs no DNS name, no certificate, and no open port but SSH. This replaced the decision "No SSH in the deploy". Do not depend on Tailscale or on any other network product: a user of one uses the SSH way with it.
- No build on the server. `chasen deploy` builds the image where it runs (the developer's computer, or CI) and the server pulls it. Through SSH, the default (user, 3 October 2026: "default to something that works, then support others like github"; "I don't like overloading the server"), the image goes to a registry in Docker on that computer (`chasen-registry`, `127.0.0.1:5555`, `localreg.go`), and the server pulls it through a port on its own loopback that `ssh -R` opens back to it for the time of the deploy: no registry on the internet, no token, nothing kept on the server. On the web (a token: CI), the image goes to `ghcr.io/<owner>/<repository>` of the git origin on GitHub. `image:` in `chasen.yml` names a registry for both ways. The registry login comes from `registry:` in `chasen.yml`, then `GHCR_TOKEN`/`GITHUB_TOKEN` (CI), then what `docker login` saved, then `gh auth token`. `--tag` deploys an existing image with no build. A directory with `image:` in `chasen.yml` and no `Dockerfile` has nothing to build: `chasen deploy` there deploys `latest`, and the server gives it a real version (`imageVersion`: the label of the image, or the start of its id). `chasen deploy <image>` (user, 7 October 2026) deploys an image that another repository releases, from any directory and with nothing of it, named after the image or `-a` (`deployRelease`). It sends `keep_settings`, so the same line again updates the app and the server keeps the settings it saved. The command is `deploy`, not `enable` (user, same day). The domain is `--domain`, like every deploy (user, 8 October 2026: "didn't we have --domain instead of the plain domain? review and align"): `chasen deploy ghcr.io/acme/chat --domain chat.example.com`. The plain word after the image, from v0.10.0, still works so nothing breaks, but no doc, usage text, or page shows it. A folder with `image:` in `chasen.yml` stays the way for an image that needs settings (user: "we should keep a way to deploy with chasen.yml"). With no build, a missing registry login is not an error: the server pulls a public image with none. The one exception is a static website (an `index.html`, no `Dockerfile`): the server copies its files into a Caddy image. Do not add a registry service to the server.
- `chasen deploy --server <user>@<host> --domain <domain>` is the whole first run (`--server` since 8 October 2026, user: "could make people understand that --server and --domain are not always needed"; the server as a plain word still works, and the docs no longer show it; `--server` also picks the server of any other command, over `server:` in chasen.yml) (user, 2 October 2026: "no chasen server add"): a server that this computer does not know is added first, then the deploy runs (`serverLogin` in `login.go`). A server it knows is used for that command only; the current server stays. The docs lead with this one command. `chasen add server` stays as the login with no deploy, for a second computer.
- `chasen bucket` sets the bucket of the server from the CLI (user, same day). It is in `protocol.ServerCommands`, not in `protocol.Commands`: a command about the server itself, which a service in front of servers must not pass on. The secret access key travels in the request body. The API does not restart for it: the replica loop of `serve` reads the settings again.
- `chasen add server <user>@<host>` is for a self-hosted server, through SSH, and it installs and sets up `chasen-server` on a machine that has none (`serverToken` in `login.go`). The login is a token of its own, from `chasen-server login`: the token of the server itself never leaves the server. `chasen add server <domain>` is the same server through its address on the web.
- The open source version does not harden a server (user, 2 October 2026). `chasen add server` puts `chasen-server` on a machine that has none, the first time, and sets it up. That is all it changes there. No firewall, no SSH settings, no system updates: the operating system is the owner's. `chasen-server check` reports what is missing, and the docs say how to fix it by hand. Do not add a `harden` command. Chasen does not set automatic updates of the operating system either (user, 3 October 2026): "we do recommend, but automated updates are not something Chasen sets, we recommend it for users to do it". The docs recommend unattended upgrades and a nightly reboot, as steps for the owner, and the alerts `updates` and `reboot` report and link to them. Chasen updates itself (`chasen-server`), not the server: say "Chasen updates itself", never "the server updates itself".
- The base domain of a server is optional (`chasen-server setup` with no `--domain`). Without one, the API has no address on the web, and a new app must bring its domain: `chasen deploy --domain shop.example.com` (`Settings.Domain`, `protocol.AppDomains`). An app that runs keeps its domains: the flag never moves it. No `domain:` key in `chasen.yml`: the deploy is imperative. The CLI keeps several logins: `chasen servers`, `chasen use`, and `server:` in `chasen.yml`.
- One owner for each server. No users or permissions on a server.
- The matcha engine (`github.com/karloscodes/matcha`) does the proxy, HTTPS, and the container swap. Chasen imports it.
- Litestream and SQLite are inside `chasen-server`. It must build with `CGO_ENABLED=0`: the binary runs in an Alpine container.
- All the state of the server is in SQLite (`/etc/chasen/server.sqlite3`): its settings (domain, token, bucket, `auto_update`, `heartbeat_url`), the apps (`apps.go`: one row for each app, the record that the engine deploys), the settings that the client sent for each app, the logins, and the activity feed. There is no config file and no file of apps: the engine gets the record in the call (`DeployApp`). A server from before copies `config.yml`, `apps.yml`, and `env/<app>.json` once and leaves the files for a rollback. It copies `apps.yml` again only when the file changes after that, because then a previous version wrote it. That one-time copy of `config.yml` is also an interface: a script can write the file with a domain and a token, then run `setup`. Programs outside this repository use it. Do not remove it.
- A bucket is optional. A server without one is complete: backups stay on its disk. No message calls that an error.
- The deploy is imperative. No desired-state file, no reconcile loop. One opt-in exception (user, 7 October 2026: "do it", and the name `--auto-update`, not `--follow`): `chasen deploy <image> --auto-update` saves `auto_update` with the app, and the API deploys the newest image of that tag once a night at 05:30 UTC (`autoupdate.go`, from the minute loop of `cron.go`), like Watchtower's default of once a day: a bad release has a day to be pulled. Only an image in a registry that the server pulls with no login; a deploy that builds, an image of the computer, or a website refuses the flag. A deploy with neither `--auto-update` nor `--no-auto-update` keeps what the app has (`mergeSettings`), and a restart keeps it too. It replaced "updates belong to the products' install scripts": an app deployed from an image had nothing on the server to update it.
- A server updates itself: `setup` installs a systemd timer that runs `chasen-server update` each night (`update.go`). It takes the newest GitHub release, checks the checksum, and goes back to the previous binary when the API does not answer. So a tag `v*` reaches every server within a day: tag only what passed the end-to-end test. `chasen-server settings auto_update off` turns it off.
- `chasen.yml` is not a docker-compose file. An unknown key is an error.
- `chasen-server adopt <app>` takes over an app that matcha runs on the same server (`adopt.go`): the record moves from the file of matcha to the database of Chasen, as it is, and nothing restarts. It works because Chasen and matcha share the proxy, the container names, and the data directories. An adopted app is like an addon: its image is not one that Chasen made, so `restart` starts it from its record, with no env of the standard added. `--undo` gives it back.
- `chasen-server quiet-hour` prints the hour of the day with the fewest requests, from the log of the proxy (`quiet.go`). It is a local command, not a protocol command. Chasen does not write the reboot hour of a server: the operating system is the owner's.
- **The open source version does not mention the cloud** (user, 7 October 2026: "for now cloud is not part of the equation so let's not pollute oss with it"). No `chasen login`, no `cloud` server name, no `--on`/`--new`, no server choice, and no word of it in the README, the docs, the usage, or the code of the CLI. The `protocol` and `oauth` packages keep the exported types that another repository uses (`Placement`, `ServerHeader`, `ServerCommands`): removing them breaks that build. Say nothing about how a hosted service works inside: not in code, comments, docs, this file, or a commit message. When a change here serves a hosted service, give the general reason ("for a server behind a proxy"). Do not name other products, with one exception: the README compares Chasen with Kamal and ONCE (user, 8 October 2026: "lets mention it here"). Examples use `ghcr.io/acme/chat`, and the docs and the landing name no other product. `bin/public` checks the files and the new commit messages for names from the inside of the cloud, and CI runs it. It knows names, not ideas: the rule is yours to keep.
- `chasen run <command>` runs one command in the container of the app (`serverRun`): the words go to `docker exec` as they are, with no shell and no input, and the history keeps the run. It is not a console.
- Cron jobs (user, 3 October 2026: "I think we can add cronjobs"): `cron:` in `chasen.yml`, a list of `schedule` (the 5 fields of cron, UTC, or @hourly/@daily/@weekly/@monthly) and `run`. They travel in `Settings.Cron` with each deploy and restart, and `protocol/cron.go` parses and checks them for the CLI and the server. The API looks at the start of each minute (`cron.go`) and runs a due job with `chasen-server run`: no shell, in the container that runs now, as `cron <command>` in the history, which keeps 20 runs of each job. The last minute it looked at is in the table `cron_state`, so a restart of the API skips no minute and runs none twice; after more than 10 minutes away it runs only the jobs of now. A job that still runs does not start again. Background jobs run in a jobs container: see the next decision.
- Jobs (user, 3 October 2026: "let's try to do as Kamal does for jobs, we don't want to run jobs along the app in the same container"; "we need to make jobs and app containers deploy as a single unit"): `jobs: <command>` in `chasen.yml` (`Settings.Jobs`) gives an app a second container, `<app>_jobs` or `<app>_jobs-next` (an app name has no `_`), from the same image with the same env, binds, memory, network, and log settings, copied from the web container through the Docker API (`jobs.go`). `apply` makes the two one unit: the web swap first (its migrations run first, like Kamal), then the new jobs container must run 10 seconds; if it stops, the web goes back to the record before and the old jobs container, never stopped, stays. Then the old one gets SIGTERM with 30 seconds. Restore stops the jobs before the swap of the databases. `chasen logs jobs`, the status, and the alerts know it. One jobs command per app, no scaling: more waits for a need.
- Images: the server keeps the newest 5 images of each app (`pruneImages`, like Kamal's `retain_containers`), for `chasen rollback`. The CLI keeps the newest 5 of each app in the Docker of the computer and in the local registry, and deletes the others after a deploy (`cleanLocalImages`, with `REGISTRY_STORAGE_DELETE_ENABLED` and `registry garbage-collect`). The registry runs with its cache of layers off (`REGISTRY_STORAGE_CACHE_BLOBDESCRIPTOR=`): the collection runs while the registry runs, and the cache kept the layers it removed, so a push of the same image again left a tag with no manifest (found 7 October 2026); a registry from before is made again with its volume.
- `chasen ssh` is the console (user, 2 October 2026): a shell in the container of the app, with a terminal. It is not SSH and it does not reach the server: a WebSocket to the API (`protocol/shell.go`), and the API asks the Docker socket for the terminal (`cmd/chasen-server/shell.go`). "No SSH in the deploy" stays true. The WebSocket code is `golang.org/x/net/websocket`, a module the build had already.
- `chasen download` saves the databases of one backup as a `tar.gz` file (`download.go`). It is the answer to "it is my data". `ssh` and `download` are `GET` requests, not commands: they are not in `protocol.Commands`.
- The CLI updates itself for a person at a terminal (user, 3 October 2026: "add auto update or some way to pull new versions easily"; this replaced "the CLI does not update itself"). Once a day it looks for a newer release, and after a command that worked, or when the screen closes, it installs it with the checksum check and says so in one line (`autoUpdate` in `update.go`). Never in CI, never for a `dev` build, never with `CHASEN_NO_UPDATE_CHECK`. A file that needs sudo is not replaced: it prints `sudo chasen update`. So the install script puts the CLI in `~/.local/bin` when that is on the `PATH`, and where chasen is already when it is installed.
- The screen (`chasen` with no command) is for watching and running a server, not for deploys. A deploy needs the directory of an app (its commit, its Dockerfile, its `chasen.yml`), and the screen is about the whole server. Do not add a deploy key.
- The screen and the bar of a desktop must not stress a server, or the computer (user, 3 October 2026: "keep things sane ... most people will have multiple apps but just a few servers"). They keep their connections open: the screen is one process, and the bar runs one `chasen overview --watch`, not a new `chasen` for each ask. Each new SSH login costs about a second. They ask for what runs with one `overview` call for all apps, not one call for each app: every 10 seconds on the screen, every minute in the bar, and every 5 seconds, or every second for the output, only while a change runs. The alerts, the app list, and the other servers come once a minute. On the server, the hot commands read the containers from the Docker socket (`containers()`), not by starting the `docker` CLI: measured on matcha-prod, that CLI was most of the 270 ms of CPU that one poll took.
- The server saves the output of a command to its history while the command runs (once a second, `saveActivity`), so `chasen history <id>` and the screen can follow a deploy that is on its way.
- The screen uses no TUI library: `golang.org/x/term` and escape codes. It shows the output of protocol commands and runs protocol commands, nothing else. A new thing on the screen needs its command first. It cleans every line of server output before it draws it (`clean`), so a server cannot send escape codes to the terminal.
- To work on the CLI and its screen, use `mise run dev` (`bin/dev`). It starts two mock servers (`internal/mock`, run by `tools/mock`, on ports 4777 and 4778): processes that answer the real protocol over HTTP with made-up apps and run no Docker. Two, so the screen shows its tree of servers. Then it runs `chasen` from source against them, in a small website directory, with logins of its own in `tmp/dev/home`: the real logins of the developer stay out. `mise run dev -- status` runs one command, and `mise run dev -- deploy` deploys through the real CLI to the mock. When a command of the server changes its output, change the mock too.
- The secrets of an app have the ergonomics of Rails credentials (user, 2 October 2026; `cmd/chasen/secrets.go`): `chasen secrets edit` opens them in `$EDITOR` and encrypts them into `chasen.secrets.enc`, which goes into git. The key is `chasen.key` (ignored by git, looked for in the directory and then in each one above) or `CHASEN_KEY`. AES-256-GCM from the standard library: no dependency. Every name in the file is a secret of the app, with no list in `chasen.yml`. `secrets:` with `secrets_command` stays for people with another secret manager. There is no command that stores a secret on the server only: the server must never be the only copy.
- The secret key of an app (`SECRET_KEY_BASE`, also given as `PRIVATE_KEY`) is made by the server at the first deploy and kept in the record of the app. A deploy can bring it as a secret instead (`secrets: [SECRET_KEY_BASE]`): then that value wins, and a new server gets the same key (`Settings.SecretKey`). These two are the only names of the standard that the settings can set. At the first deploy of a new app with a secrets file, the CLI makes the key and saves it in that file (`keepSecretKey`); it never does that for an app that runs already.
- Addons (`chasen enable fusionaly|formlander|lognorth`) run products from their images.
- Backups cover every volume of an app (`/var/matcha/<app>/*`). An app turns its backups off with `backup: false` in `chasen.yml` (`Settings.NoBackup`, `backedUp` in `backup.go`): no hourly snapshot, no backup before a deploy, no live replica, no restore from the bucket. It is for data that an app makes again at each start, like a demo. The hourly run removes the stale live replica of such an app from the bucket and keeps its old snapshots.
- The retention of the live replica is fixed in `litestream.go` (user, 2 October 2026: "apply sane retention"): one full copy each day at 00:00 UTC, full copies kept one day. Litestream keeps the changes since the full copy that it deleted, so the replica holds one full copy and the changes of one to two days, and the first cleanup is at the second midnight (checked on matcha-prod, 3 October 2026). It is not a setting: the history is the job of the snapshots (24 hours, 7 days, 4 weeks, 6 months). `chasen bucket` prints what the bucket holds for each app and by kind of replica file (`usage.go`), so its size and growth are visible. The setup of the replica is ours to get right (user, same day: "I'll let you setup the right litestream setup for us"), so there are two checks in `verify.go`: `chasen verify` restores the replica and the newest snapshot next to the real databases, checks them, and removes them; and the hourly run fails, and stops the heartbeat, when a replica misses transactions of its database for more than 10 minutes. That check reads the positions that Litestream itself keeps (the replica daemon writes them to the table `replica_state` every 10 seconds). Do not compare file times: a checkpoint changes the time of a database with no new data, and a first version that did so gave false alarms. The compaction levels stay the ones of the library (30 seconds, 5 minutes, 1 hour): another layout under a replica that exists is a risk for its restore.
- The replica process (`chasen-server replicate`) must never open and close a database that it replicates, nor its `-wal` or `-shm` file. On Linux a process that closes a file loses every lock it holds on that file, also the locks of Litestream in the same process, and a replica with no locks uploads whole databases again. `findDatabases` takes the files that the process holds and leaves them closed, and `locks_test.go` reads the locks from `/proc/locks`. `CHASEN_DEBUG=1 chasen-server replicate`, for a run by hand, prints each sync of Litestream and the reason of each full copy.
- `chasen alerts` says what is wrong with a server (an error) or puts it at risk (a warning), each with its fix (user, 3 October 2026: "warnings or errors from your server, hardening and maintenance, refreshed every 1m"). It is a server command (`protocol.ServerCommands`). The server looks on each call, from files and Docker, with nothing in the background (`alerts.go`). The API container sees `/etc` and `/run` of the host read-only under `/host` (`CHASEN_HOST`), so the checks read files and run no host program. The screen asks every minute and counts them in the top line; `!` shows them. `chasen-server settings quiet_alerts <name>` turns one off, for a firewall of the provider. Alerts report and never fix: the operating system is the owner's. `chasen-server check` with no app prints the same alerts; the engine's own check is not used any more.

## Rules for changes

- A new command goes in `protocol` first, then in `cmd/chasen-server/server.go`. The CLI passes every protocol command through.
- Tests use real SQLite, real Docker, a real S3 store, and a real private registry (`registry:2` with a password). No mocks.
- The standard is in `STANDARD.md` and in code. The rules that need no Docker are in `protocol/standard.go` (`Settings.Check`, `ShapeOf`, `CheckAppName`, `CheckVolumes`, `StandardEnv`): the CLI applies them before a deploy and the server applies them again, so a rule exists one time. `chasen check` (`check.go`) tests a running container. A rule that changes must change in the document, the code, and the check.
- `chasen deploy`, `check`, and `restart` review the app first (`cmd/chasen/review.go`): `chasen.yml` before the build, the image after the build and before the push. A finding is an error (cannot work: the deploy stops) or a warning (often fails: the deploy goes on), and each one says what to write and links to a page of the docs. A new finding needs a row in the table of `docs/deploy.md`. Keep warnings few: a warning on every deploy teaches people not to read them.
- The documents in `docs/` and `STANDARD.md` are also the docs of chasenhq.com: the site copies them. Write them for a reader who has no access to this repository.
- The server pulls an image under its real name and keeps it under the local name `chasen.invalid/<app>:<version>`. It tells matcha not to pull (`SkipPull`). One workaround waits for a change in matcha: domains are joined with a comma in one field.
- The settings of an app travel in the body of `deploy`, `check`, and `restart`: one line of JSON, then the files of a website. There is no `env` command.
- A client reads each response to its end (`Client.Run`): a response that is closed early takes its connection with it. Through SSH a connection is a login to the server, and the screen sends about ten commands every few seconds, so the SSH client keeps at most four connections and uses them again (`protocol/ssh.go`). Before v0.7.7 the screen made about 80 logins a minute and loaded a small server.
- The README is the pitch and a table of contents. The manual is `docs/`. Do not put manual text back into the README.
- In examples, the base domain of a server is `example.com` (not `apps.example.com`), and a second server is `example.org`.

## Releases

Never tag a commit that has `[ci skip]` in its message: GitHub then skips the release workflow too, and the tag makes no release. That happened to `v0.6.1`, which is a tag with no release; `v0.6.2` is the same code.

A tag `v*` runs `.github/workflows/release.yml`: it builds the CLI (macOS and Linux) and the server (Linux), and attaches them to a GitHub release with `checksums.txt`. The install scripts `chasenhq.com/cli` and `chasenhq.com/server` download the newest release.
